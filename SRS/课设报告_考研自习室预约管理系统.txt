摘要
本课程设计完成了一个面向考研自习室场景的预约管理系统。系统采用前后端分离架构，后端基于 Spring Boot 3、MyBatis-Plus 和 MySQL 实现业务逻辑与数据持久化，前端基于 Vue 3、Vite 和 Axios 实现交互界面。系统围绕“学生预约座位、学生签到、管理员管理资源、管理员处理违规与黑名单、学生信誉查询”等核心业务展开，构建了用户表、自习室表、座位表、预约表和黑名单表五个主要数据实体。

本系统重点实现了以下功能：学生端支持登录、查看自习室、可视化选座、按日期与时间段预约、取消预约、签到、查看我的预约、查看黑名单状态与违规记录；管理员端支持自习室与座位管理、批量生成座位、预约记录分页筛选、黑名单管理、学生用户管理，以及对逾期未签到预约的自动扫描与违规判定。系统对预约规则进行了较严格的约束，例如同一学生每天可在上午、下午、晚上三个时间段各预约一次，同一时间段同一座位只能被一人有效占用，超过规定签到时间未签到则会自动判定为违约并加入黑名单。

课程设计结果表明，该系统能够较完整地覆盖自习室预约管理的主要业务流程，数据库表结构设计清晰，前后端职责划分明确，系统具备较好的可维护性与扩展性，能够满足课程设计对数据库建模、系统实现、测试分析和文档撰写的基本要求。

关键词：数据库课程设计；自习室预约；Spring Boot；Vue 3；MySQL；前后端分离

1 项目内容、要求与分组情况总体介绍
1.1 项目内容
本课程设计的项目内容为设计并实现一个“考研自习室预约管理系统”。系统主要服务于有固定学习时间安排的学生群体，支持学生按日期、时间段和座位进行预约，并支持签到、取消、查看历史预约等操作；同时支持管理员维护自习室资源、管理预约记录、处理违规、管理黑名单以及维护学生账号。

与一般的简单座位预约系统相比，本系统更强调数据库建模与业务规则落地。例如：
（1）系统以自习室、座位、预约、黑名单等为核心对象建立关系模型；
（2）系统区分学生与管理员两类角色，并通过会话鉴权和角色拦截控制权限；
（3）系统支持时间段预约与签到规则判断；
（4）系统支持预约记录筛选、分页、自动违规处理等具有一定完整度的管理功能。

1.2 项目要求
根据课程设计任务要求，本系统需要完成以下工作：
（1）进行需求分析，明确系统角色、业务流程和数据库实体关系；
（2）设计数据库表结构并建立实体之间的联系；
（3）实现前后端交互功能，包括学生端和管理员端；
（4）完成系统联调与测试，验证核心业务是否正确；
（5）撰写课程设计报告，说明设计思路、实现方法、测试过程及总结。

2.2 任务分析
2.2.1 任务分析
考研自习室场景具有以下特点：
（1）学生需要快速查看可用自习室和空闲座位；
（2）预约必须受时间段约束，避免无限制占座；
（3）签到规则要明确，否则预约行为无法真正约束；
（4）管理员需要维护房间和座位资源，并能处理预约冲突、违规记录和黑名单；
（5）系统既要体现数据库课程设计中的数据建模能力，也要具备基本可用的业务闭环。

因此，本系统的核心任务可以概括为：围绕“用户—资源—预约—违规”四条主线，建立数据库模型，实现学生预约与管理员管理两大类功能，并通过规则控制提升系统完整性。

2.2.2 系统设计目标
本系统的设计目标如下：
（1）实现学生与管理员双角色登录；
（2）实现自习室、座位、预约、黑名单等核心数据的增删改查；
（3）实现学生按日期和时间段预约座位；
（4）实现座位可视化展示，便于学生像选电影票一样选座；
（5）实现预约签到、取消预约、逾期自动判违；
（6）实现管理员对预约、黑名单和学生信息的维护；
（7）在保证功能完整性的同时，使系统界面清晰、业务逻辑尽量严谨。

2.3 需求分析
2.3.1 功能要求
系统功能需求分为学生端和管理员端两部分。

一、学生端功能
（1）用户登录与退出；
（2）查看当前开放的自习室列表；
（3）选择日期和时间段后查看座位状态；
（4）通过可视化座位图选择座位；
（5）提交预约；
（6）取消尚未签到的预约；
（7）对当日预约进行签到；
（8）查看我的预约记录；
（9）查看当前黑名单状态；
（10）查看个人违规记录。

二、管理员端功能
（1）新增、修改、启用/停用、删除自习室；
（2）按房间管理座位；
（3）在新增自习室时批量自动生成座位，减少手工录入工作量；
（4）查看预约记录，并按学号、自习室、日期、时间段、状态筛选；
（5）对预约记录进行分页展示；
（6）手动取消预约或手动标记违约；
（7）扫描逾期未签到预约并自动处理；
（8）新增黑名单记录、解除黑名单；
（9）对黑名单记录进行分页展示；
（10）新增、修改、删除学生账号；
（11）删除学生时，若存在未来预约，需二次确认并自动释放相应座位资源。

三、业务规则要求
（1）同一学生每天在上午、下午、晚上三个时间段中，每个时间段最多保留一条有效预约；
（2）同一时间段内，同一座位只能被一人有效预约；
（3）学生不能预约过去的日期；
（4）若当天某时间段已开始，则不能再预约当天该时间段；
（5）上午签到时段为 8:00-12:00，超过 8:30 未签到视为违规；
（6）下午签到时段为 14:00-17:00，超过 14:30 未签到视为违规；
（7）晚上签到时段为 18:00-22:00，超过 18:30 未签到视为违规；
（8）被黑名单封禁的学生不能继续预约；
（9）取消某时间段预约后，该学生可以重新预约该时间段的其他座位。

2.3.2 数据要求
本系统主要涉及五类核心数据：
（1）用户数据：保存学生和管理员的登录身份、姓名、角色等信息；
（2）自习室数据：保存房间名称、楼层、总座位数、开放状态等；
（3）座位数据：保存座位所属房间、座位编号、是否靠窗、是否有插座、是否损坏等；
（4）预约数据：保存学生、座位、日期、时间段、预约状态、创建时间等；
（5）黑名单数据：保存学生学号、违规原因、违规时间、封禁状态等。

其中预约数据是整个系统的核心业务数据，它与学生、座位、自习室以及黑名单逻辑均有联系，因此在设计时需要重点考虑其完整性、一致性和状态流转。

2.3.4 系统 E-R 图说明
本节原本应插入系统 E-R 图，现用文字说明代替。

系统主要实体及联系如下：
（1）用户（User）与预约（Reservation）之间是一对多关系，即一个学生可以对应多条预约记录；
（2）自习室（Room）与座位（Seat）之间是一对多关系，即一个自习室包含多个座位；
（3）座位（Seat）与预约（Reservation）之间是一对多关系，即一个座位在不同日期、不同时间段可产生多条预约记录；
（4）用户（User）与黑名单（Blacklist）之间是一对多关系，即一个学生在历史上可能产生多条违规记录；
（5）预约记录通过 seat_id 与座位关联，再通过 room_id 间接关联到自习室。

若后续补图，可将以上实体画成 E-R 图，并标出主键、外键和联系基数。

2.3.5 数据库关系视图说明
本节原本应插入关系模式图，现用文字说明代替。

数据库关系模式可表示为：
（1）User(id, student_id, password, real_name, role, create_time)
（2）Room(id, room_name, floor, total_seats, status)
（3）Seat(id, room_id, seat_number, has_window, has_power, status)
（4）Reservation(id, student_id, seat_id, reservation_date, time_slot, status, create_time)
（5）Blacklist(id, student_id, reason, violation_date, status)

其中：
（1）Seat.room_id 关联 Room.id；
（2）Reservation.seat_id 关联 Seat.id；
（3）Reservation.student_id 逻辑上关联 User.student_id；
（4）Blacklist.student_id 逻辑上关联 User.student_id。

之所以在预约表与黑名单表中使用 student_id 而不是 user_id，是为了在业务层用学号直接关联学生身份，便于系统按学号查询预约和违规记录。

2.3.6 系统设计流程图说明
本节原本应插入流程图，现以文字形式描述主要流程。

一、学生预约流程
登录系统 -> 进入预约大厅 -> 选择自习室 -> 选择日期与时间段 -> 查看座位图 -> 选择空闲座位 -> 提交预约 -> 系统校验黑名单、时间规则、同日同时间段限制和座位占用 -> 预约成功 -> 等待签到。

二、学生签到流程
进入“我的预约” -> 选择待签到记录 -> 点击签到 -> 系统校验预约归属、日期是否到达、是否在允许签到时间内 -> 成功签到或提示失败 -> 若超时则自动判定违规。

三、管理员处理流程
管理员登录 -> 进入资源管理/预约管理/黑名单管理/学生管理页面 -> 根据功能进行增删改查 -> 系统更新数据库并返回结果。

四、自动判违流程
定时任务按固定时间间隔运行 -> 扫描所有待签到预约 -> 判断是否已超过各时间段签到截止时间 -> 若超时则将预约状态改为违约并写入黑名单记录。

2.4 功能模块设计
本系统可以划分为以下几个功能模块：

（1）用户与鉴权模块
负责登录、退出、获取当前会话用户信息，并区分学生与管理员权限。

（2）学生预约模块
负责学生查看开放自习室、查看座位状态、选择座位、提交预约、取消预约、签到、查看预约记录。

（3）信誉与黑名单模块
负责查询黑名单状态、违规记录、封禁状态控制、手动或自动加入黑名单、解除黑名单。

（4）资源管理模块
负责管理员对自习室和座位资源进行维护，包括新增房间、自动生成座位、修改座位属性、删除房间与座位。

（5）预约管理模块
负责管理员对预约记录进行筛选、分页、取消预约、标记违约、扫描逾期预约。

（6）学生管理模块
负责管理员新增、修改、删除学生账号，并在删除时联动处理未来预约。

3 具体实现
3.1 类设计
系统后端主要采用分层结构，包括 domain、controller、service、config、task 等层次。

一、实体类（domain）
（1）User：用户实体，对应 user 表；
（2）Room：自习室实体，对应 room 表；
（3）Seat：座位实体，对应 seat 表；
（4）Reservation：预约实体，对应 reservation 表；
（5）Blacklist：黑名单实体，对应 blacklist 表。

二、控制器层（controller）
（1）UserController：处理登录、退出和当前用户信息；
（2）RoomController：面向学生查询开放自习室及座位信息；
（3）ReservationController：面向学生处理预约、签到、取消、查看我的预约；
（4）BlacklistController：面向学生查询黑名单状态与违规记录；
（5）AdminRoomController：管理员维护自习室；
（6）AdminSeatController：管理员维护座位；
（7）AdminReservationController：管理员维护预约记录；
（8）AdminBlacklistController：管理员维护黑名单；
（9）AdminStudentController：管理员维护学生账号。

三、业务层（service）
其中 ReservationService 是本系统最核心的业务层接口，主要负责预约规则校验、签到规则校验、自动判违、未来预约释放等功能。

四、配置与拦截层（config）
（1）AuthInterceptor：校验登录状态；
（2）AdminInterceptor：校验管理员权限；
（3）WebMvcConfig：注册拦截器并配置跨域；
（4）MybatisPlusConfig：配置分页插件。

五、定时任务层（task）
ReservationOverdueTask 用于周期性扫描逾期未签到预约，并自动处理违规。

六、前端结构
前端主要分为：
（1）views：页面组件，区分 student 与 admin 两类页面；
（2）components：复用组件，如 SeatMapBoard 座位图组件；
（3）api：接口封装；
（4）router：路由配置；
（5）stores：会话状态管理。

3.2 模块及实现代码介绍（部分）
3.2.1 登录与权限控制模块
系统采用会话方式进行身份认证。登录时，后端根据学号和密码查询用户表，若成功则在 HttpSession 中写入当前登录用户信息。随后由拦截器对需要登录的接口进行保护，并对管理员接口额外进行角色校验。

前端路由部分根据当前用户角色进行分流：
（1）学生登录后进入学生端；
（2）管理员登录后进入管理员端；
（3）未登录用户访问受限页面时会被重定向到登录页。

该设计具有实现简单、权限边界清晰的特点，适合作为课程设计项目的鉴权方案。

3.2.2 自习室与座位查询模块
学生进入预约大厅后，系统会先读取所有开放的自习室，再根据所选房间、日期和时间段查询座位状态。后端会把该日期、该时间段下已被有效预约的座位标记为不可用，前端则在座位图上以红色展示不可选座位，从而实现可视化选座。

为了提高交互体验，系统加入了“类似电影院售票”的座位图：
（1）每个座位以座位号显示，如 A-01、A-02；
（2）可用座位可点击选择；
（3）不可用或损坏座位显示为红色；
（4）当前选中的座位会有明显高亮。

管理员在新增自习室时，可以选择“自动生成座位”，只需输入排数和每排座位数，系统即可批量生成 A-01、A-02 这类规范编号，大幅减少手动录入工作量。

3.2.3 预约、取消与签到模块
预约模块是系统的核心业务模块，实现时主要考虑了以下规则：
（1）黑名单用户不能预约；
（2）同一天的同一时间段，学生只能保留一条有效预约；
（3）同一时间段同一座位只能被一人占用；
（4）当天若某时段已开始，则不能再预约当天该时段；
（5）学生取消某一时段预约后，可重新预约该时段的座位。

为避免并发下出现重复预约，后端在 ReservationServiceImpl 中为“用户-日期-时间段”和“座位-日期-时间段”分别建立锁键，在预约时按排序后的锁键加锁，降低并发冲突概率。

签到模块按时间段规则工作：
（1）上午可在 8:00 后签到，8:30 后未签到判违约；
（2）下午可在 14:00 后签到，14:30 后未签到判违约；
（3）晚上可在 18:00 后签到，18:30 后未签到判违约。

系统还实现了自动判违功能：定时任务周期性扫描待签到记录，若已超过截止时间，则自动将预约状态改为违约，并写入黑名单表。

3.2.4 管理员管理模块
管理员模块包含四部分：

（1）资源管理
支持新增、修改、启用/停用、删除自习室；支持增删改座位；支持批量生成座位；支持在房间删除时连带删除其下全部座位。

（2）预约管理
支持按学号、自习室、日期、时间段、状态筛选预约记录；支持分页显示；支持管理员取消预约；支持管理员手动标记违约；支持一键扫描逾期预约。

（3）黑名单管理
支持手动新增黑名单记录；支持查看黑名单历史；支持解除封禁；支持分页显示，提升管理可读性。

（4）学生管理
支持新增学生账号、修改学生信息与密码、删除学生账号。最新版本中，删除学生时不会再因历史预约或历史黑名单记录而失败；如果该学生存在未来预约，系统会先给出二次确认提示，确认后自动取消这些未来预约并释放相关座位。

4 运行调试与分析讨论
4.1 用户登录模块测试
测试内容：
（1）学生使用正确账号密码登录；
（2）管理员使用正确账号密码登录；
（3）错误密码登录；
（4）未登录访问受保护页面。

测试结果：
（1）学生和管理员均可按角色进入对应页面；
（2）错误账号或密码会提示登录失败；
（3）未登录访问管理页面时，系统能正确跳转回登录页；
（4）管理员与学生权限隔离正常。

4.2 学生预约与选座模块测试
测试内容：
（1）查看开放自习室；
（2）切换日期和时间段刷新座位状态；
（3）选择空闲座位提交预约；
（4）预约后再次查看座位图，已预约座位是否变红；
（5）取消预约后是否可以重新预约；
（6）能否预约当天已开始的时间段。

测试结果：
（1）系统能正确展示房间和座位；
（2）已预约座位会被标记为不可用；
（3）同一学生同一时间段不能重复保留有效预约；
（4）取消后可重新预约；
（5）若当前时间已过某时间段开始时间，则不能再预约当天该时段；
（6）整体流程符合设计预期。

若本节需要插图，可放置“预约大厅页面”“座位图页面”“预约成功提示”等截图；本稿以文字说明替代。

4.3 管理员资源管理模块测试
测试内容：
（1）新增自习室；
（2）使用自动生成座位功能批量创建座位；
（3）修改自习室信息；
（4）删除带有座位的自习室；
（5）停用与启用自习室状态。

测试结果：
（1）新增自习室成功；
（2）批量生成座位成功，编号规则正确；
（3）修改房间信息后能即时生效；
（4）删除自习室时可连同其下座位一起删除；
（5）停用后学生端不再展示该房间，启用后恢复展示。

4.4 黑名单与自动判违模块测试
测试内容：
（1）学生预约后故意不签到；
（2）管理员执行逾期扫描；
（3）等待定时任务自动扫描；
（4）检查预约状态是否改为违约；
（5）检查黑名单表是否新增记录；
（6）检查学生端是否被禁止继续预约；
（7）管理员解除黑名单后是否可恢复预约。

测试结果：
（1）超过签到截止时间的待签到预约会被正确判为违约；
（2）系统会自动写入黑名单记录；
（3）被封禁的学生无法再次预约；
（4）解除封禁后学生可恢复正常预约；
（5）说明自动判违链路完整可用。

4.5 学生删除与预约释放模块测试
测试内容：
（1）删除只有历史预约记录的学生；
（2）删除有未来预约的学生；
（3）删除有未来预约时是否出现二次确认；
（4）确认删除后，该学生未来预约是否被取消；
（5）原先占用的座位是否重新变为可预约。

测试结果：
（1）只有历史记录的学生可以直接删除；
（2）存在未来预约的学生第一次删除时会收到确认提示；
（3）确认删除后，系统会自动取消这些未来预约；
（4）原占用座位会重新释放，学生端可再次预约；
（5）说明学生删除逻辑和预约资源释放逻辑已形成闭环。

5 设计体会与小结
通过本次课程设计，我对数据库系统从需求分析到落地实现的全过程有了更完整的理解。以前在课堂中更多接触的是数据库表、SQL 语句和范式等静态知识，而在实际项目中，我需要把这些知识转化成真正可运行的系统，这使我更加理解“数据库设计不仅是建表，更是业务规则建模”的含义。

在本项目中，我最大的收获主要体现在以下几个方面：
（1）进一步掌握了数据库建模方法，能够围绕业务对象抽取实体并建立联系；
（2）学会了将业务规则映射为数据库查询条件和状态流转逻辑；
（3）理解了前后端分离项目中接口设计、权限控制和页面交互的基本思路；
（4）认识到系统测试的重要性，很多问题都是在实际演示过程中逐步暴露并修正的；
（5）提高了文档整理能力，能够按照课程设计模板对项目进行系统性总结。

当然，系统仍有可以继续完善的地方。例如：
（1）可以增加统计报表，如自习室利用率、学生违约次数排行等；
（2）可以增加更细粒度的封禁策略，如累计多次违约自动延长封禁时间；
（3）可以进一步美化前端界面，并加入更多操作提示；
（4）可以将密码改为加密存储，以提高安全性；
（5）可以增加单元测试和接口自动化测试，提升系统工程化程度。

总体来看，本次课程设计较好地完成了“数据库原理及应用课程设计”的目标。系统实现了较完整的业务流程，数据库结构较清晰，界面交互较直观，具备课程设计可交付的基本质量。
